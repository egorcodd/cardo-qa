# Cardo: надёжность истории и обработки событий

История операций Grafana читается из `banking.operation_history`. Это одно завершённое событие на операцию, без второй строки входящей проводки, посевных транзакций и частных реквизитов. Kafka и Elasticsearch показывают отдельные этапы доставки, а не определяют существование перевода.

По умолчанию история показывает 7 дней, оперативные Prometheus-панели имеют относительный период 1 час. Недельный запрос ко всем техническим графикам не нужен для наблюдения текущего состояния и существенно увеличивает нагрузку при общем обновлении раз в 10 секунд.

## Конфигурация

- Grafana 13.2.4: 1 GiB, SQLite WAL, 3 повтора запроса, 5 повторов транзакции, 2 соединения метаданных. Копировать работающую SQLite через backup API; одного файла при активном WAL недостаточно.
- PostgreSQL: `unless-stopped`. Новые роли `cardo_telemetry` и `cardo_grafana`; production-пароли генерируются отдельно. `TELEMETRY_DATABASE_URL` и `GRAFANA_HISTORY_PASSWORD` обязательны в защищённом proxy-развёртывании.
- Роль telemetry владеет только своей схемой. Роль Grafana получает USAGE двух схем и SELECT только двух представлений: `banking.operation_history`, `telemetry.pipeline`. Ей не выдаются права `cardo_qa`, доступ к исходным таблицам, запись или создание объектов.
- Сначала создать роли/схему (`infra/postgres/init.sh` для разработки, закрытое provisioning в production), затем миграции banking 006 и telemetry 001–002, затем сервисы и datasource. Существующие миграции не изменены.
- Kafka хранит текущие темы 7 дней с прежним ограничением 256 MiB на раздел. Этот предел может сократить фактическую глубину. Технические логи Elasticsearch по-прежнему хранятся 3 дня; бизнес-проекция имеет отдельные суточные индексы и политику 30 дней.

## Доставка

1. KafkaJS вызывает `acceptEvent` и ждёт атомарной записи PostgreSQL. До успешного ответа обработчик не завершается, поэтому offset не подтверждается. Обработку служебных транзакционных записей выполняет штатный KafkaJS runner.
2. Ключ SHA-256 от topic + eventId сохраняется в постоянной таблице. Различие безопасного содержимого при том же ключе отмечается PAYLOAD_CONFLICT. Сырые повреждённые сообщения и персональные поля не сохраняются.
3. Воркер отправляет до 100 записей, разбирает статус каждого bulk item. 201/409 завершают запись; временные ошибки повторяются с паузой до 5 минут, ошибки схемы помещаются в карантин.
4. Конкретный индекс `cardo-events-YYYY.MM.DD` и ID определяются один раз исходной датой и ключом. Повтор после неопределённого ответа не попадает в другой индекс при rollover. PostgreSQL остаётся главным источником дедупликации.
5. Восстановление использует `origin=recovered`, исходные даты и те же ключи. `kafka_observed_at` остаётся NULL до фактического получения Kafka. Повторное индексирование не выполняет финансовые операции и не публикует прошлые события в engagement.

Обычные HTTP-логи остаются ограниченной очередью best effort, с явным счётчиком отброшенных записей. Бизнес-события через неё не проходят.

## Восстановление процессов

Оба consumer наблюдают GROUP_JOIN, HEARTBEAT, STOP, DISCONNECT, REBALANCING, CRASH. При окончательном CRASH процесс завершается с ошибкой; если heartbeat/восстановление отсутствуют 60 секунд, срабатывает тот же путь. Обычный простой с heartbeat не считается отказом. Штатная остановка закрывает наблюдение до disconnect. Docker `unless-stopped` возвращает завершившийся процесс; статус unhealthy сам по себе не перезапускает контейнер.

Продюсер с fencing/непригодным состоянием или шестью последовательными неудачами также запрашивает контролируемый перезапуск. В логах остаётся безопасный класс ошибки, без адресов, секретов и текста исключения. Временный повтор может доставить событие снова; существующий engagement inbox предотвращает повторное создание уведомления. Учебные сценарии ошибок сохранены.

Lag проверяется по группам каждые 15 секунд. Доступный диапазон `high-max(committed,low)` отделён от `max(low-committed,0)` уже удалённых позиций. Offset -1 означает отсутствие позиции. Смещения не сбрасываются принудительно.

## Проверки

`node --test tests/reliability.test.mjs` проверяет lifecycle, ожидание постоянной записи, карантин, bulk retry, стабильный индекс, права структуры дашборда.

`TEST_DATABASE_URL=.../reliability node tests/reliability-integration.mjs` запускается только на одноразовой тестовой базе; создаёт и пересоздаёт схемы этой базы. Проверяет реальные SQL, дедупликацию, конфликт, повтор и запрет чтения/записи частных таблиц.

`TEST_DATABASE_URL=.../reliability TEST_KAFKA_BROKER=reliability-kafka:9092 node tests/reliability-kafka-integration.mjs` использует отдельный брокер: транзакционные записи, повтор, повреждённое сообщение, heartbeat при простое, окончательный CRASH.

`node services/telemetry/recover.ts --dry-run /private/manifest.json` сохраняет фиксированный список ключей и отпечатков безопасных проекций. `--apply` с тем же файлом повторяемо добавляет только эти записи, проверяя исходное содержимое. Подключения BANKING_DATABASE_URL и DATABASE_URL передаются закрыто; скрипт не публикует Kafka и не выполняет банковские операции.

После выпуска проверить native Grafana health/datasources/query, обе группы Kafka с участниками, pending/quarantine, исходные банковские агрегаты, память/OOM/рестарты. Отдельная метрика `cardo_grafana_up` проверяет Grafana из telemetry; её отказ виден независимо от самой Grafana. Внешний канал уведомления владельцу этим выпуском не подключается.

Суточное наблюдение следует отличать от короткого нагрузочного испытания. Конкретные замеры и ограничения находятся в отчёте выпуска E-QA от 28 октября 2026 года.

## Откат

Сохранить старые образы, закрытые настройки, согласованную SQLite-копию и PostgreSQL dump до применения. При откате вернуть прежние образы banking/engagement/telemetry, файлы datasource/dashboard и параметры Grafana; новые таблицы/представления оставить, не удаляя принятые записи. Отдельные индексы бизнес-проекции также не удалять. Восстановление старого полного PostgreSQL dump поверх новых пользовательских операций не является безопасным штатным откатом.

# События, метрики и логи Cardo

Инструменты работают с действиями в Cardo. После пополнения или перевода Banking сохраняет операцию и событие в одной транзакции PostgreSQL. Обработчик outbox публикует событие в Kafka; Engagement читает его, учитывает eventId в inbox и создаёт уведомления и баллы.

## Запуск на своём компьютере

Нужен запущенный Docker. Выдели ему минимум 8 ГБ памяти. Из папки репозитория выполни:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.observability.yml ps -a
```

Первый запуск скачивает образы, создаёт темы Kafka, источники Grafana и раздел Cardo в Kibana. У db-setup, kafka-setup, elastic-setup и tools-setup завершение с кодом 0 нормально.

| Инструмент | Адрес по умолчанию | Что смотреть |
| --- | --- | --- |
| Cardo | http://localhost:8942 | Результат операции, история и уведомления |
| Swagger | http://localhost:8942/api/docs | Контракт запросов и ответов |
| Kafka UI | http://localhost:8085 | События, partition, offset и consumer groups |
| Grafana | http://localhost:3003/d/cardo-overview | Запросы, ответы 500, время ответа, outbox и обработка событий |
| Kibana | http://localhost:5602/s/cardo/app/discover | Логи сервисов по времени, service, requestId и eventId |

Учебный вход во все три инструмента: **student / cardo_student_dev**. Права — только чтение. Если меняешь порты или учебный пароль в .env, используй свои значения.

Для остановки используй те же два файла:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml down
```

Обычный down сохраняет volumes. Следующий up продолжит работу с теми же аккаунтами, событиями и журналами. Базовый запуск с одним docker-compose.yml использует HTTP-доставку outbox и подходит для практики на компьютере без полного набора инструментов.

## Проследить свою операцию

1. Зарегистрируй вымышленный аккаунт. Открой DevTools → Network и выполни пополнение или перевод. Запиши время, запрос, статус и X-Request-Id из заголовков ответа. Сохрани operationId, если он есть в ответе.
2. В Kafka UI открой тему **cardo.practice.events.v1** и найди сообщение с этим requestId. Сравни type, amount, currency и operationId с действием. Запиши eventId, partition и offset. У каждого события есть своя позиция; offset имеет смысл вместе с темой и partition.
3. В Kibana открой Cardo → Discover, выбери **Cardo logs** и интервал последних 15 минут. Введи в поисковой строке KQL:

   ```text
   requestId: "идентификатор-из-ответа"
   ```

   Добавь колонки service, message, status, eventId, topic, partition и offset. Сопоставь запрос Gateway, обработку Banking и обработку события Engagement. Для поиска по одному сервису добавь `and service: "banking"`. Время в браузере и UTC может отображаться по-разному.
4. В Grafana открой дашборд **Cardo — сервисы и события** и выбери тот же интервал. Посмотри число запросов, статусы и время ответа. Отдельно доступны ответы 500–599, ответы 404 и таблица статусов по сервисам и маршрутам. Панели с подписью «с запуска сервисов» показывают накопленные счётчики, остальные — изменения за указанный интервал. Панели событий показывают публикацию и обработку; outbox и lag помогают понять, где накопилась очередь.
5. Вернись в Cardo. Проверь баланс, историю, баллы и уведомление. Наличие сообщения в Kafka само по себе не доказывает, что все последующие действия выполнены.

Логи поступают пакетами, а метрики собираются каждые 5 секунд. Если свежая запись ещё не видна, обнови Discover и проверь выбранное время. Для сравнения нескольких запросов сохрани каждый requestId отдельно.

## Темы и группы

| Ресурс | Назначение |
| --- | --- |
| cardo.practice.events.v1 | Учебная проекция событий: сумма, валюта, requestId, eventId и операция |
| cardo.practice.dead-letter.v1 | События, для которых обработка завершилась ошибкой после повторных попыток |
| cardo-practice-audit | Читает учебную проекцию и добавляет запись о наблюдении события в логи |
| cardo-engagement | Обрабатывает бизнес-события и создаёт результат в Engagement |

Рабочая тема cardo.banking.events.v1 доступна сервисам. Для учебного просмотра используется отдельная проекция без имени, телефона, email, полного номера карты и содержимого авторизации. В ней accountRef — обезличенный идентификатор.

Lag на дашборде — разница между конечной позицией темы и сохранённой следующей позицией группы, отдельно для каждой partition. Нулевой lag не доказывает правильность бизнес-результата: проверяй также логи обработчика и интерфейс.

## Проверка повторной обработки в своей копии

Сначала сохрани eventId и результат обычной операции. Останови только обработчик:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml stop engagement
```

Выполни пополнение. Посмотри событие в Kafka и рост отставания cardo-engagement в Grafana. Затем запусти обработчик:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml up -d --no-deps engagement
```

Дождись обработки, проверь lag, историю и уведомления. Остановка и управление группами выполняются только владельцем своей локальной копии. На общем стенде ученический аккаунт может лишь читать сообщения и показатели.

## Хранение и доступ

Kafka хранит события до 3 дней с ограничением размера сегментов. Prometheus сохраняет метрики до 3 дней или 512 МБ. Для журналов Elasticsearch настроены ежедневный rollover или 256 МБ на shard и удаление через 3 дня после rollover. Это политика хранения, а не жёсткая квота всего Docker-диска.

Брокер Kafka и Elasticsearch не публикуют порты на компьютере. Интерфейсы привязаны к 127.0.0.1. Подписки, пароли, сессии и данные E-QA в этот набор инструментов не передаются. Сборщик получает только разрешённые поля, работает без Docker socket и не читает журналы чужих контейнеров.

Для размещения на сервере нужны закрытые пароли сервисов, HTTPS и отдельные права учеников. Демонстрационные значения из .env.example предназначены для локальной копии. Вход в E-QA и вход в инструменты — отдельные сессии.

Для оператора подготовлен [порядок выпуска и отката](OBSERVABILITY-DEPLOYMENT.md).

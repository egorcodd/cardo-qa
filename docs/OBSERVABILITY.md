# События, метрики и логи Cardo

Инструменты работают с действиями в Cardo. После пополнения или перевода Banking сохраняет операцию и событие в одной транзакции PostgreSQL. Обработчик outbox публикует их в отдельные потоки Kafka. Engagement читает внутренние события, учитывает eventId в inbox и сохраняет уведомления и баллы. Вместе с уведомлением он сохраняет событие в notification_outbox; отдельный обработчик доставляет это событие в Kafka.

## Запуск на своём компьютере

Нужен запущенный Docker. Выдели ему минимум 8 ГБ памяти. Из папки репозитория выполни:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.observability.yml ps -a
```

Первый запуск скачивает образы, создаёт темы Kafka, источники Grafana и раздел Cardo в Kibana. У db-setup, kafka-setup, elastic-setup и tools-setup завершение с кодом 0 нормально.

| Инструмент | Адрес по умолчанию | Что смотреть |
| --- | --- | --- |
| Cardo | http://localhost:8942 | Результат операции, история и уведомления |
| Swagger | http://localhost:8942/api/docs | Контракт запросов и ответов |
| Kafka UI | http://localhost:8085 | События, partition, offset и consumer groups |
| Grafana | http://localhost:3003/d/cardo-overview | Запросы, ответы 500, время ответа, outbox и обработка событий |
| Kibana | http://localhost:5602/s/cardo/app/discover | Логи сервисов по времени, service, requestId и eventId |

Учебный вход во все три инструмента: **student / cardo_student_dev**. Права — только чтение. Если меняешь порты или учебный пароль в .env, используй свои значения.

Для остановки используй те же два файла:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml down
```

Обычный down сохраняет volumes. Следующий up продолжит работу с теми же аккаунтами, событиями и журналами. Базовый запуск с одним docker-compose.yml использует HTTP-доставку outbox и подходит для практики на компьютере без полного набора инструментов.

## Проследить свою операцию

1. Зарегистрируй вымышленный аккаунт. Открой DevTools → Network и выполни пополнение или перевод. Запиши время, запрос, статус и X-Request-Id из заголовков ответа. Сохрани operationId, если он есть в ответе.
2. В Kafka UI открой **Cardo practice → Topics → cardo.topups.v1** для пополнения или **cardo.transfers.v1** для перевода. На вкладке Messages выбери Latest, обнови список после действия и найди свой requestId. Сравни type, amount, currency и operationId с действием. Запиши eventId, partition и offset. Затем открой **cardo.notifications.v1**: requestId должен связывать события одной операции, causationId уведомления — ссылаться на eventId операции. Сопоставь notificationId с ответом API GET /api/notifications.
3. В Kibana открой Cardo → Discover, выбери **Cardo logs** и интервал последних 15 минут. Введи в поисковой строке KQL:

   ```text
   requestId: "идентификатор-из-ответа"
   ```

   Добавь колонки service, message, status, eventId, causationId, notificationId, topic, partition и offset. Сопоставь запрос Gateway, обработку Banking и обработку события Engagement. Для поиска по одному сервису добавь `and service: "banking"`. По исходному событию можно искать `eventId: "uuid-операции" or causationId: "uuid-операции"`. Время в браузере и UTC может отображаться по-разному.
4. В Grafana открой дашборд **Cardo — сервисы и события** и выбери тот же интервал. Посмотри число запросов, статусы и время ответа. Отдельно доступны ответы 500–599, ответы 404 и таблица статусов по сервисам и маршрутам. Панели с подписью «с запуска сервисов» показывают накопленные счётчики, остальные — изменения за указанный интервал. Панели событий показывают публикацию и обработку; outbox и lag помогают понять, где накопилась очередь.
5. Вернись в Cardo. Проверь баланс, историю, баллы и уведомление. Наличие сообщения в Kafka само по себе не доказывает, что все последующие действия выполнены.

Логи поступают пакетами, а метрики собираются каждые 5 секунд. Если свежая запись ещё не видна, обнови Discover и проверь выбранное время. Для сравнения нескольких запросов сохрани каждый requestId отдельно.

## Топики: что и когда появляется

| Топик | Кто публикует | Что означает сообщение |
| --- | --- | --- |
| cardo.transfers.v1 | Banking | Сохранён перевод клиенту Cardo или в другой банк |
| cardo.topups.v1 | Banking | Сохранено пополнение счёта |
| cardo.notifications.v1 | Engagement | Сохранено уведомление об операции, награде, напоминании или предложении |
| cardo.processing-errors.v1 | Engagement | Обработчик завершил три попытки с доменной ошибкой; сообщение перенесено в очередь ошибок |

Пустой топик означает, что подходящих событий ещё не было или срок хранения истёк. Сам по себе пустой топик ошибок не говорит об отказе Kafka. События пополнения и перевода появляются после сохранения операции, а уведомления — после сохранения соответствующего результата в Engagement. Событие создания уведомления не подтверждает доставку Web Push на устройство.

Внутренние топики cardo.internal.transfers.v1 и cardo.internal.topups.v1 доступны сервисам. Ученик читает отдельную проекцию без имени, телефона, email, полного номера карты, текста уведомления и содержимого авторизации. accountRef — обезличенный идентификатор аккаунта; это техническая связь, не имя человека.

### Поля сообщения

| Поле | Как использовать |
| --- | --- |
| eventId | Идентификатор события. При повторной доставке того же события он сохраняется |
| requestId | X-Request-Id исходного HTTP-запроса; у фонового напоминания или предложения может отсутствовать |
| type | Вид события: banking.transfer.completed, banking.external-transfer.completed, banking.top-up.completed или engagement.notification.created |
| occurredAt | Время создания события в UTC; доставка может произойти позже |
| operationId | Операция в истории Cardo; для служебных уведомлений может отсутствовать |
| amount, currency | Сумма строкой и валюта операции; у события уведомления эти поля отсутствуют |
| notificationId | ID сохранённого уведомления, который можно сверить с API |
| causationId | eventId исходной операции, вызвавшей уведомление; у фоновых событий может отсутствовать |
| kind | Вид уведомления; сравни с ответом API |
| category | Группа настроек уведомлений: transactions, service или offers |
| sourceTopic, sourcePartition, sourceOffset | Исходная позиция события в очереди ошибок |
| attempts, errorCode, status, failedAt | Число попыток, код ошибки, статус и время завершения обработки |

Суффикс v1 относится к контракту топика. Поле version банковского события сохраняет версию исходного события, в том числе 2 для перевода между аккаунтами Cardo. Название топика и это поле не обязаны совпадать.

У операции и созданного уведомления разные eventId. Схема связи:

```text
cardo.topups.v1        eventId=A, requestId=qa-topup-001, operationId=tu-...
cardo.notifications.v1 eventId=B, causationId=A, requestId=qa-topup-001,
                       notificationId=..., kind=top_up, operationId=tu-...
```

В Kafka UI фильтр сообщения можно составить через поиск requestId в JSON. Сохраняй тройку «топик, partition, offset»: offset не уникален между топиками или partition. Ключ сообщения — accountRef. Порядок гарантируется внутри partition одного топика, общего порядка переводов, пополнений и уведомлений нет. После сбоя публикации возможна повторная доставка с тем же eventId; сравнивай уникальные события с записями API.

### Группы обработчиков

| Группа | Что читает | Что проверять |
| --- | --- | --- |
| cardo-engagement | Внутренние переводы и пополнения | Событие обработано, результат сохранён в Engagement |
| cardo-practice-audit | Четыре учебных топика | Событие наблюдается в Kibana с topic, partition и offset |

Kafka UI читает сообщения для просмотра. Это не обработчик бизнес-операции и не подтверждение её результата.

Lag на дашборде — разница между конечной позицией темы и сохранённой следующей позицией группы, отдельно для каждой partition. Нулевой lag не доказывает правильность бизнес-результата: проверяй также логи обработчика и интерфейс.

## Практика по трём потокам

1. Выполни обычное пополнение и сохрани ответ API. Найди событие в cardo.topups.v1, затем связанное уведомление в cardo.notifications.v1. Сверь баланс, историю и API уведомлений.
2. Выполни перевод другому своему вымышленному аккаунту Cardo. Найди событие в cardo.transfers.v1. Сопоставь связанные уведомления с результатом отправителя и получателя, включая ID их операций.
3. Выполни перевод в другой банк. Сравни type и результат с переводом внутри Cardo: внешний банк используется для имитации перевода.
4. Проследи служебное уведомление, например о награде. Установи, есть ли у него исходный HTTP-запрос, операция и causationId. Отсутствующее необязательное поле не заменяй вымышленным значением.
5. Для каждой проверки сохрани запрос, ответ, связанные события и логи. Если результат расходится с требованиями, воспроизведи сценарий и оформи баг-репорт. Пароли, Bearer token и cookie в материалы не включай.

## Проверка повторной обработки в своей копии

Сначала сохрани eventId и результат обычной операции. Останови только обработчик:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml stop engagement
```

Выполни пополнение. Посмотри событие в Kafka и рост отставания cardo-engagement в Grafana. Затем запусти обработчик:

```sh
docker compose -f docker-compose.yml -f docker-compose.observability.yml up -d --no-deps engagement
```

Дождись обработки, проверь lag, историю и уведомления. Остановка и управление группами выполняются только владельцем своей локальной копии. На общем стенде ученический аккаунт может лишь читать сообщения и показатели.

## Хранение и доступ

Kafka хранит события до 3 дней с ограничением размера сегментов. Prometheus сохраняет метрики до 3 дней или 512 МБ. Для журналов Elasticsearch настроены ежедневный rollover или 256 МБ на shard и удаление через 3 дня после rollover. Это политика хранения, а не жёсткая квота всего Docker-диска.

Брокер Kafka и Elasticsearch не публикуют порты на компьютере. Интерфейсы привязаны к 127.0.0.1. Подписки, пароли, сессии и данные E-QA в этот набор инструментов не передаются. Сборщик получает только разрешённые поля, работает без Docker socket и не читает журналы чужих контейнеров.

Для размещения на сервере нужны закрытые пароли сервисов, HTTPS и отдельные права учеников. Демонстрационные значения из .env.example предназначены для локальной копии. Вход в E-QA и вход в инструменты — отдельные сессии.

После обновления стенда новые операции публикуются только в топики выше. Старые cardo.practice.events.v1 и cardo.practice.dead-letter.v1 сохраняются оператору для истории и отката, но не отображаются student. Внутренняя прежняя тема cardo.banking.events.v1 остаётся в подписке Engagement для завершения уже опубликованных событий. Историю и offset при обновлении не сбрасывают; старые записи не копируют в новые топики.

Для оператора подготовлен [порядок выпуска и отката](OBSERVABILITY-DEPLOYMENT.md).

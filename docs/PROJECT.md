# Как устроен Cardo

Cardo использует микросервисную архитектуру и работает как учебный банк с вымышленными деньгами. Репозиторий открыт, чтобы можно было клонировать его, работать с Git, запускать свой стенд и сравнивать интерфейс, API, логи и SQL. В приложении намеренно есть ошибки; этот документ описывает ожидаемые правила, а не перечисляет ответы к практике.

## Запуск и данные

Нужны Docker Engine/Desktop с Compose и Git. После клонирования выполни `docker compose up -d --build`; приложение и Swagger доступны по адресам из README. Новый обычный аккаунт получает три карты и счета RUB/USD/EUR с нулевыми балансами. Начать практику можно с учебного пополнения. Тестовые получатели отличаются от обычных аккаунтов: у них подготовленные вымышленные данные.

PostgreSQL хранится в volume `cardo-data`. `docker compose down` сохраняет данные; `docker compose down -v` удаляет учебную базу. Для локальной SQL-практики есть роль `cardo_qa` с чтением четырёх схем; её локальный пароль `cardo_qa_dev`. Адрес `localhost:5434`, база `cardo`. Это демонстрационная конфигурация, не реквизиты доступа к внешнему серверу.

## Архитектура

Микросервисная архитектура включает пять приложений в Compose: gateway, customer, banking, engagement и rates. Каждый запускается в отдельном контейнере со своим процессом, проверкой здоровья и логами. Gateway обслуживает интерфейс и направляет API-запросы владельцу данных. Клиент обращается через gateway; внутренние порты сервисов наружу не публикуются.

Customer владеет профилями и сессиями, Banking счетами и операциями, Engagement наградами и уведомлениями, Rates курсами валют. PostgreSQL один; у сервисов разные схемы и роли. Сервисы обмениваются HTTP-запросами и событиями через outbox/inbox, без чтения чужих SQL-таблиц. Общие контракты находятся в `packages/contracts`, технические функции в `packages/shared`, реализация в `services/<name>`.

`db-setup` выполняется один раз для подготовки схем и локальных ролей. Завершение с кодом 0 нормально. Состояния доступны через `docker compose ps -a`, логи через `docker compose logs banking` и аналогично для других сервисов. `/health` gateway проверяет здоровье зависимостей; `/api/health` показывает доступность самого публичного API. Сервер создаёт `X-Request-Id` для каждого запроса и передаёт его между сервисами. Этот идентификатор возвращается в заголовке ответа и помогает найти связанные записи в логах. Заполнять его вручную не нужно.

## Переводы и обмен

| Валюта перевода | Комиссия Стандарт | Комиссия Плюс |
| --- | --- | --- |
| RUB | 500 ₽ | 100 ₽ |
| USD | 5 $ | 1 $ |
| EUR | 5 € | 1 € |

Перевод между клиентами Cardo идёт между счетами одной валюты. Валюта отправителя определяется выбранной картой. При поиске получателя по телефону укажи `currency`; при поиске по номеру карты валюта определяется найденной картой. Разные валюты в одном переводе не конвертируются. Перевод во внешний банк является имитацией рублёвого перевода, без обращения к реальной платёжной системе.

У отправителя списываются сумма и отдельная комиссия в той же валюте; получателю зачисляется сумма без комиссии. В истории должны быть операция перевода и комиссия. Замороженная карта не должна расходовать деньги. Для обмена своих счетов используется отдельный `/api/exchange` с курсом и версией Rates.

Сумма положительная, максимум два знака после точки. Передавай её строкой, например `"10.25"`. Для пополнения, перевода и обмена нужен `Idempotency-Key`: повтор с тем же ключом и теми же данными не должен повторно менять баланс. Для новой операции используй новый ключ, для обмена ключ с префиксом `ex-`.

## Swagger и практика API

Swagger: `/api/docs`. Машиночитаемая спецификация: `/api/openapi.json`; адрес API в ней `/api`, без двойного префикса. Регистрация и вход возвращают `user` и непрозрачный `token`. В браузере используется cookie; в Postman выбери Bearer Token и вставь token из ответа. В Swagger Authorize также вставляется только token.

1. Создай два вымышленных аккаунта; у каждого своя сессия.
2. Получи `/api/cards`, выбери валюту и пополни счёт отправителя.
3. Найди второго клиента через `/api/recipients/resolve` в той же валюте.
4. Передай полученный `recipientId`, `cardId`, сумму и новый `Idempotency-Key` в `/api/transfer`.
5. Сравни ответ, балансы обоих аккаунтов, историю, уведомления и SQL.

Ошибки имеют JSON-формат `error.code` и `error.message`. При проблеме сервиса сопоставляй ответ с `X-Request-Id` и логами. Схемы и правила в Swagger описывают ожидаемый контракт. Найденное расхождение нужно исследовать и оформить в баг-репорт.

## PWA и сборка

Стенд поддерживает установку PWA и Web Push при поддержке браузером. Подписка берётся из PushManager конкретного устройства. Уже доставленные уведомления не меняются при обновлении приложения. Отображение системной подписи уведомления зависит от ОС.

Production-сборка автоматически обфусцирует код интерфейса; библиотеки вынесены отдельно. DevTools, Network, Charles/Fiddler, API, логи и SQL остаются доступными. Исходники репозитория читаемые. Для разработки можно установить Node.js 24+, выполнить `npm ci`, `npm run build` и `npm run dev`; база и внутренние адреса настраиваются отдельно. Для просмотра интерфейса в режиме разработки используй Vite с конфигурацией `apps/web/vite.config.js`.

Kafka, Grafana и Kibana в текущий Compose не входят. Правила публикации данных перечислены в [SECURITY.md](../SECURITY.md).
